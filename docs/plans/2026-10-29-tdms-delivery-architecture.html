addon-file-summariser

Delivery: from writing straight to InfluxDB to a polled HTTP API

Explains commits a696319 and 03515cc — “Write TDMS points using the Sparkplug historian's Influx schema” and “Add rest api and store” Branch dn/influx-format

This add-on used to write summarised TDMS points directly into InfluxDB with its own measurement/tag shape. It now writes nothing to InfluxDB at all: it stages points locally and serves them over a small HTTP API, which a dedicated acs-edge REST connection polls and republishes as ordinary Sparkplug metrics — the same path every other device's data takes, through the normal Sparkplug historian. (Auth moved separately in this same branch — see 2026-10-26-auth-keytab-to-password.html for that change.)

Before: a direct InfluxDB write, in its own shape

Bypassed the normal Sparkplug/historian pipeline entirely — this was the only thing in the whole stack writing to InfluxDB directly rather than via Sparkplug.

Every row became a point in measurement tdms_summary, tagged with group and channel (plus file and topLevelInstance). That shape doesn't match how acs-data-access expects to query a device's metrics — per-metric queries (mean in /v1/series, metric-filtered exports) key off the measurement name, and this put every channel of every file under the one shared tdms_summary measurement, collapsing them together in a whole-device export.

After: stage locally, serve over HTTP, let Sparkplug carry it the rest of the way

Everything right of the pod is the pipeline every other device's data already goes through — this add-on now only has to look like one more Sparkplug-publishing device.

Channel naming: borrowing the Sparkplug historian's own convention

Rather than inventing another shape for the new path, points are named to match historian-sparkplug's own convention: metric <channel>:d (always a float, per the :i/:u/:d/:b/:s type-suffix convention), published under Sparkplug path <group> — omitted rather than sent empty when a channel has no group. Each channel ends up queryable through acs-data-access as <group>/<channel>, the same as any other Sparkplug metric on any other device:

// Before (lib/influx.js, deleted)
measurement: "tdms_summary"
tags: { group, channel, file, topLevelInstance }

// After (republished via Sparkplug by acs-edge, written by historian-sparkplug)
metric name: `${channel}:d`
Sparkplug path: group   // omitted if there is no group
→ queryable as `${group}/${channel}`

A channel name containing /, or ending in one of the type-suffix tokens itself, will collide with this convention and be mis-parsed downstream — noted in a code comment and in the README rather than guarded against. Points summarised under the old tdms_summary shape aren't migrated; files summarised before this change need re-summarising to become queryable under the new one.

What the HTTP API actually serves

  1. Discovery: GET /v1/devices/:device_uuid/channels

    For an admin wiring up a new device/channel in the Manager, not meant to be polled on a schedule. Each channel gets a stable channel_id — a hash of group+channel, not the raw names, since TDMS names are free-form and may contain characters unsafe in a URL path.

  2. Polling: GET /v1/devices/:device_uuid/channels/:channel_id

    Returns points newer than this endpoint's own high-water mark for that channel, advanced on every successful call — steady-state polling after the first successful delivery returns nothing new rather than replaying the backlog. Always 200 with [] for nothing pending, never 404, so the edge agent's poll loop (any non-200 is treated as an error) stays simple.

  3. Retention, not a delivery guarantee

    Points are kept and re-served to every poll until retentionHours (default 24) after they were staged, not after their own sample timestamp. InfluxDB overwrites by exact timestamp, so re-delivering something already ingested is wasted work, not corruption — but something never polled within the window is dropped silently when it ages out.

  4. Basic auth, not Factory+-mediated

    The polling endpoint checks API_USERNAME/API_PASSWORD (from a Secret you create yourself, api.authSecret.name) — unlike this service's own Factory+ calls, this credential has nothing to do with Kerberos/Auth, it's unmediated the same way the InfluxDB token this path replaces used to be.

Why this is considered better

From the commit message

“Points were written as measurement tdms_summary with group/channel tags, which acs-data-access can't match for per-metric queries (mean in /v1/series, metric-filtered exports) and which collapses every channel into one metric in whole-device exports.”

Trade-off, stated explicitly

This add-on now keeps local state (the pending-points store) and depends on something else (acs-edge) actually polling it within retentionHours or data is silently dropped — a fire-and-forget direct write never had that failure mode. In exchange, data now goes through the same pipeline, with the same per-metric query shape, as everything else in the stack.
