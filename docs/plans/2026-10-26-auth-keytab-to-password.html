Auth: how it moved from a Kerberos keytab to a username/password

Explains commit 52f006b — “Change from keytab auth to user pass auth” Branch dn/influx-format

The add-on authenticates to the rest of Factory+ (ConfigDB, Directory, Files, Auth) as its own service principal, sv1filesummariser. It always did this by presenting a credential to the central Auth service and exchanging it for a short-lived opaque bearer token, which is then attached to every other request. What changed is which credential it presents — a Kerberos keytab, swapped for a plain username/password — and that removes an entire subsystem (local krb5 config, keytab volumes, a kinit wrapper process) from the pod.

Before: keytab + GSSAPI

Needed a direct network path from the pod's krb5 library all the way to the KDC/kadmin in core's namespace.

The KerberosKey custom resource asked the operator for a Random secret and wrote it as a keytab into file-summariser-keytabs/client. The deployment mounted that keytab plus a generated krb5.conf (built from factoryPlus.realm, baseUrl and coreNamespace), and the container's actual entrypoint command was wrapped:

command: [ "/usr/bin/k5start", "-Uf", "/keytabs/client" ]
args: [ "node", "bin/summariser.js" ]

k5start is a background kinit daemon — it used the keytab to get a Kerberos ticket into a ccache (KRB5CCNAME), kept renewing it, and only then exec'd the real Node process as a child. Inside the app, ServiceClient (via Fetch._gss_fetch) saw no username/password option set, so it fell through to the GSSAPI branch: build a SPNEGO context against HTTP@<auth-host>, negotiate with the Auth service's /token endpoint, and verify mutual auth. That exchange is what actually needed a live route to the realm's KDC/kadmin, not just to the Auth service itself.

After: username + password

No KDC hop. The pod only ever talks HTTP to Factory+ services it was already calling.

The KerberosKey resource now asks for type: Password instead of Random, and writes a plaintext password into file-summariser-password/password. The deployment template sets that straight into the container as two env vars:

- name: SERVICE_USERNAME
  value: sv1filesummariser@<realm>
- name: SERVICE_PASSWORD
  valueFrom:
    secretKeyRef:
      name: file-summariser-password
      key: password

No more k5start wrapper, no mounted keytab, no krb5.conf — the deploy/templates/krb5-conf.yaml template is deleted outright, and factoryPlus.baseUrl / factoryPlus.coreNamespace (which only existed to let that krb5.conf find the KDC/kadmin across namespaces) drop out of values.yaml entirely. The only Factory+ coordinate the chart still needs, besides the Directory URL, is factoryPlus.realm — now used purely to build the principal name.

What actually happens on each request (client code)

  1. RxClient({ env }) picks up the two vars

    bin/summariser.js constructs the service client with { env: process.env }. ServiceClient's opts_from_env maps SERVICE_USERNAME → username and SERVICE_PASSWORD → password on its options.

  2. First real request needs a token

    Any call through Fetch.fetch() (ConfigDB watch, Files lookup, etc.) routes through do_fetch, which has no forwarded JWT and no bearer_jwt option set, so it asks service_token() for a bearer token for that service's base URL.

  3. _fetch_token calls POST /token on the Auth service

    This goes through _gss_fetch, which now takes the Basic-auth branch because username and password are both set:

    Authorization: Basic base64(sv1filesummariser@REALM:<password>)

    The Auth service checks that password against the realm's Kerberos database itself (it already has a direct line to the KDC, being part of core) and, if it's valid, returns an opaque bearer token in the JSON body.

  4. Token is cached and reused

    Fetch.tokens caches that token per service base URL, so only the first request to a given service pays the /token round trip. Every subsequent call attaches Authorization: Bearer <token> directly.

  5. 401 triggers exactly one retry

    If a downstream service rejects a cached token (expired, revoked), do_fetch retries once, passing the known-bad token into service_token() so it fetches a fresh one instead of reusing the stale cache entry.

Why this is considered safe

From the README

“This add-on only needs HTTP reachability to Auth/ConfigDB/Files/Directory — it authenticates with a username/password (verified server-side against Kerberos by whichever service receives the request), so it never needs direct network access to the KDC itself.”

Trade-off, stated explicitly

The credential is now a server-generated password sitting in a k8s Secret in plaintext, rather than a keytab blob. The README is careful to note this is the same exposure level as before — both are just Secret contents, equally readable by anyone with Secret access in the namespace — not a new class of risk, just a more legible one.
